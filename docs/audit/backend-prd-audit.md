# Backend PRD audit — 21 October 2026

The backend has working candidate intake, strict round-robin assignment, application stages, local versioned documents and durable incoming IMAP processing. It does not yet implement the complete v1 workflow specified by the twelve-page Recruitment CRM PRD. The largest gaps are transactional stage correctness, the task scheduler, medical repeats and reopening, consistent candidate identity handling, user management and reporting.

This document records backend evidence and acceptance requirements. It does not authorize or implement the broader changes. The application, current models and source were inspected against all twelve pages in `artifacts/requirements-review.txt`. References below identify repository paths and relevant functions; line numbers describe the reviewed working tree and may move.

## Verification scope

- Reviewed API routers, stage rules, models, desk snapshot, incoming-mail worker/services and the available test inventory.
- Ran `backend/.venv/Scripts/python.exe -m pytest tests/test_file_upload.py -q -p no:cacheprovider` from `backend`: **27 passed**, one upstream Starlette/AnyIO deprecation warning.
- Ran six pure, in-process stage-rule evaluations using synthetic dictionaries. The results below are evaluator outputs, **not observations of live database/API behavior**.
- No live database, mailbox or OCR provider was used. No migration, deployment or production storage operation was performed. No PostgreSQL concurrency test or restore exercise was run during this audit.
- This is a functional requirements audit, not a complete security assessment. Findings about authorization describe the PRD's role and ownership contracts.

## Document workflow changes completed before this audit

The focused changes in `backend/app/api/routers/files.py` and `backend/tests/test_file_upload.py` address the previously requested upload/view workflow:

- Uploads validate that their client, company, candidate or application exists and that the document slot has a bounded valid identifier.
- The parent record is locked before version allocation, including a slot's first upload. This also coordinates with incoming-mail updates that already lock matched candidates.
- Upload metadata and an audit event commit together. Replacements retain earlier metadata and bytes.
- A metadata or storage failure rolls back the transaction and removes known-uncommitted partial files. If a database connection is invalidated and the commit outcome is unknown, immutable bytes are retained for reconciliation rather than risking deletion of a committed document.
- Application uploads use the existing `ensure_can_work` ownership rule. Candidate uploads remain available to signed-in users because manual entry assigns the candidate before uploading its originals; strict owner-only uploads need explicit entry/creator provenance first.
- Default viewing remains inline; `GET /api/files/{id}?download=true` requests a download. Responses use `nosniff` and `Cache-Control: private, no-store`. Known document extensions support browsers that send a generic media type.
- Unknown attachments return 404, missing/out-of-storage files return 410, concurrent metadata conflicts return 409 and storage/database failures return 503.

The tests cover upload validation, audit fields, application ownership, round-robin entry compatibility, version history, viewing/downloading both old and new files, missing files, transaction/storage failures and authentication. They use synthetic sessions and temporary files. The row-lock strategy still requires acceptance against isolated PostgreSQL under concurrent manual and email uploads. Local storage, crash reconciliation and a durable backup/restore procedure remain operational requirements. The file API change does not prove attachment ownership during stage completion; that is a separate gap below.

## Minimum acceptance package before calling v1 complete

1. Isolated PostgreSQL transactions for concurrent map, draft save, complete, unmap, reassign, last deployment and versioned upload. Assert final business rows, task counts and audits, not only HTTP status.
2. A full eleven-stage path plus each negative exit, medical repeat, Admin reopen, remap and final order-fill case. Include invalid enums/dates/numbers, whitespace fields and forged/mismatched attachment references.
3. Role-based tests for owner/non-owner/Admin/Manager calls, remarks, documents, user management, reports and exports while retaining the PRD's all-candidate Data Bank access.
4. Clock-controlled scheduler tests for 48-hour escalation, repeated reminders, end-of-day owner updates and private to-do notifications, including restart/idempotency and agency-timezone boundaries.
5. Unified manual/email identity and assignment tests, including no eligible Staff, duplicate/merge conflicts, preserved recruiter corrections, notifications and multi-person review handling.
6. Supported source/provider smoke tests and a storage/database restore exercise using approved test accounts and synthetic candidate documents.

The current test inventory is strongest around OCR, email intake, authentication and bootstrap behavior. No tests referencing `stage_by_no`, `complete_stage`, `save_draft`, `record_call`, `reassign` or `add_remark` were found in `backend/tests` during this review. The file tests added in this work do not fill those workflow acceptance gaps.
