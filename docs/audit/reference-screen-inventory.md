This is a **static implementation inventory**, not a runtime acceptance report. Source files, component mounting, handlers, API clients and selected backend routes were inspected. The reference application, database and external OCR, email, WhatsApp, attendance and payroll services were not launched or exercised. “Wired” below means a visible action has an implementation and API path in source; it does not establish that a deployed service succeeds.

This reference is an agency recruitment and employee-administration product. It is not the DCRM PRD. Its UI patterns can inform DCRM, but its permission model, assignment algorithm, callback timing, commercial relationships, recruitment states and HR modules must not replace DCRM requirements. DCRM scope and phase references remain in the [requirements matrix](../requirements-matrix.md), [implementation phases](../implementation-phases.md) and [earlier architecture comparison](../reference-architecture-review.md).

## Specific issues to avoid copying

1. **Visible export that does nothing.** `CandidatesView.tsx:615–617` renders Export CSV without a handler, link or form action. DCRM exports should either produce the authorized filtered artifact or visibly explain unavailability.
2. **Success before persistence.** `SourcingHub.tsx:486–585` and `JobOrders.tsx:722–944` announce/cache create, edit and delete operations while suppressing API errors. Submission awaits the candidate update, but `saveSubmitted()` separately suppresses the order update failure. DCRM must await authoritative writes and preserve drafts or show reconciliation errors.
3. **Heuristics presented as suitability.** `JobOrders.tsx:200–400` groups different capabilities into aliases, supplies a one-year experience default for some absent data, computes 45/35/20 weighted scores and calls some results exceptional/eligible. `parseMinExperienceYears()` treats any string containing `0` as zero, including `10`. This is not a validated fit model. DCRM should show recorded facts, exact skill matches and explicit missing evidence before considering any separately validated scoring feature.
4. **Submitted is not deployed.** `JobOrders.tsx:89–96` and `saveSubmitted()` derive filled status/count from submitted IDs. DCRM must retain distinct matched, selected and deployed numbers and the PRD opening rules.
5. **Industry inference loses real trades.** `CandidatesView.tsx:122–154` classifies any designation containing “engineer” as IT and uses a small substring vocabulary. This can misclassify mechanical/civil work and miss trade skills. DCRM grouping should use actual saved skills/designations or an explicitly managed taxonomy.
6. **No inline document viewer/version browser.** Protected original resume and identity downloads exist, but profile iframe code is hidden download fallback. No complete immutable version-history UI was found. DCRM FILE-01 remains a separate storage, API and interface acceptance requirement.
7. **Upload-format promise and OCR gate differ.** `resume_store.py` accepts PDF/Word/RTF/text and several image types. `ResumeParser._VERIS_READABLE` lists PDF/DOCX/JPEG/PNG/WebP, while uploaded-candidate intake requires a VeriIS structured source. UI acceptance is not proof every advertised format can complete extraction. DCRM should agree on supported formats across chooser, validation, conversion and provider calls.
8. **Raw file and extracted facts have different permissions.** Separate identity collection/projections are useful; full payload or Aadhaar scan must not accidentally cross a broad candidate-read boundary. Download helpers use tokens in URL queries as a CORS workaround; DCRM should retain its own authenticated file delivery rather than copy that transport pattern.
9. **Local logs are not canonical audit.** `candidateLog.ts` stores localStorage events used by unmounted log screens. Mounted review/assignment/recruitment histories are separately server-backed. DCRM needs durable actor/entity/action/time history across sessions, devices and users.
10. **Loaded collections are not scalable query contracts.** Directory filtering and match scoring are mostly browser-side. The matching endpoint requests up to 2,000 candidates; loading pages until all candidates are in memory is not equivalent to bounded server filters/full-text search. DCRM should implement the shared server query described in its architecture.
11. **Configuration is not live health.** Settings shows configured mailboxes/key presence; preview fixtures and realtime status props cannot prove ingestion is running. DCRM should continue distinguishing connection, queue state, worker heartbeat, last success and per-document errors.
12. **Reference business policies are not portable defaults.** Nationality refusals, country/job CV exemptions, branch allocation, employee payroll and finance approval rules are reference-specific. Importing a file wholesale would import these policies too.

## Useful patterns to adapt deliberately

- Keep the full candidate detail fetch separate from list projections. A form must not save a partial list record over a richer stored profile.
- Own the uploaded bytes in the CRM. Store stable file metadata/hash/backend keys and distinguish absent files from storage outages. Retain originals even when extraction needs review.
- Keep candidate details, extracted identity facts, provider payloads, documents and audit history as separate contracts with explicit visibility.
- Present skill evidence, missing requirements and document presence as inspectable facts. Preserve multiple recorded skills and trade/machinery terms; avoid invented categories.
- Preserve order filters and scroll/context when opening a candidate, then return to the same result set.
- Make every task row open the action that resolves it. DCRM should use its own task/stage rules for completion and clocks.
- Expose loading, stale-data, retry, in-progress, partial failure and success states. Do not turn a failed fetch into an empty database or a failed write into cached success.
- Pair reassignment with a reason and visible history, and independently authorize the action on the server.
- In long operations, ignore late responses from an invalidated session and provide a persistent completion link.
- Keep keyboard focus/escape behavior, responsive tables/cards, understandable field labels and usable empty states in the acceptance checklist.

| DCRM requirement family | What this reference can inform | What DCRM still needs from its own PRD and audit |
| --- | --- | --- |
