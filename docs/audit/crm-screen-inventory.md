The current implementation and acceptance evidence are tracked in [the integration report](../integration-audit.md) and [the requirements matrix](../requirements-matrix.md), including the later account administration, master-data editing, durable manual document intake, workflow and report changes.

## Reading the results

- **Connected** means the UI invokes an API mutation/read or computes a real result from the loaded CRM snapshot. It does not establish production acceptance, authorization correctness, or transaction safety.
- **Partial** means usable behavior exists but specified fields, actions, failure recovery, or role scope are incomplete.
- **Placeholder** means a visible control has no mutation or deliberately reports that the operation is unavailable.
- **Extension** means an existing product choice differs from the PDF and needs an explicit product decision, not automatic removal.

Line anchors identify the inspected working tree; later edits can move them. Source paths below are relative to the repository root.

## Roles, routing, and shared behavior

`frontend/src/shared/state/crm-store.tsx:79-101` defines capabilities: every role creates records and maps/unmaps candidates; Admin/Manager work any candidate, reassign, delete employer/order records and use personal to-dos; only Admin manages users, connects sources, exports Data Bank data and reopens stages. Staff can work only their own candidate. Admin/Manager see team reports. These frontend checks must be supported independently by backend authorization.

All workspace routes are session guarded; To-do and Users also have capability guards. Startup errors have retry, lazy routes have loading fallback, and a page error boundary wraps the router (`frontend/src/app/routes.tsx:33-115`). Most pages depend on the entire `/api/bootstrap` snapshot rather than a dedicated paginated/query API (`frontend/src/shared/state/crm-store.tsx:188-242`). A successful mutation commonly calls `refresh()` and shows a toast. The shared `run` helper rethrows failures, so callers that immediately close dialogs or clear text can lose useful retry context (`frontend/src/shared/state/crm-store.tsx:304-323`).

The sidebar has **12** destinations, including Companies and Mapped Candidates, rather than the PDF's ten. Clients are people and Companies are employers; this is a structural extension that affects navigation, order relationships and report labels (`frontend/src/app/layout/app-shell.tsx:42-54`). Staff correctly do not see To-do or Users.

## Data and integration dependencies

- The screens share users/clients/companies/designations/orders/candidates/applications/tasks/remarks/todos/notifications in bootstrap. The full snapshot makes source-side owner scoping, transfer size and pagination critical; a hidden button does not secure underlying data.
- Inbox uses its own accounts/messages/jobs endpoint and ingestion revision polling. It is a usable incoming-IMAP processing view, not the complete Gmail/Microsoft/WhatsApp/reply product specified in the PDF.
- Candidate profile OCR is a separate read; normal profile fields and raw OCR may differ. A correction workflow must define which becomes authoritative without losing evidence or recruiter edits.
- Files are versioned attachment rows. Current UI uses authenticated file URLs and explicit download; storage loss still yields server 410. Restore/storage acceptance is separate from successful typechecks.
- Reports need historical escalation/missed-update/re-medical events to satisfy specified metrics. Deriving those from current open tasks cannot recreate past performance.
- Notification delivery/read state, 15-minute SLA scans, repeat reminders, end-of-day missed updates and due to-do reminders require producers and persisted events. Showing a badge does not prove those flows exist.
- Record mutations using `run()` can commit successfully and then fail during refresh. Candidate creation now preserves ID, but employer and other create flows still need idempotent recovery to prevent duplicate creates.
