# Recruitment CRM requirements and implementation matrix

Updated 22 October 2026 after the module integration, reference-screen review and API performance pass. Source of truth: [Recruitment CRM — Developer Specification](requirements/recruitment-crm-developer-specification.pdf), 14 October 2026, all 12 pages. The [module workflow guide](workflows/README.md) separates the full scope into reviewable user journeys and acceptance checklists. The [current integration audit](integration-audit.md) records screen coverage, evidence and remaining acceptance. The [pre-implementation review](integration-audit-baseline-2026-10-21.md) and its source appendices are retained as a dated baseline; their placeholder findings must not be read as the current implementation state.

**Implemented path** means source/UI/API is connected, not production accepted. **Isolated tests** means targeted automated tests exercised the described contract; it does not mean every possible path passed. **Partial/divergence/limit** identifies retained product or scale differences. **Live pending** requires configured test accounts/providers/deployment. Historical workstream numbers retain links to the original phase plan; they are not a percentage-complete measure. No row means the production environment was migrated or deployed.

Schema additions through revision 0016 introduce owner/event history, communication receipts, durable manual document jobs, independent company WhatsApp contact, Zoho mailbox/draft state, attendance, ordered presence and the confirmed reference attendance policy, optional acknowledgement intents, person/page reviews and outgoing WhatsApp history. Current schema has 50 tables. Later user instructions restore the original multi-provider mail requirement (Gmail, Microsoft 365, Zoho and IMAP/SMTP, no account limit) and add attendance; those changes are recorded below. See [database design](database-design.md) and migration source for exact contracts. Isolated migration parity and upgrade/downgrade tests are separate from production migration approval.

## Remaining product and acceptance boundaries

- **Employer/navigation model:** the existing contact → company hierarchy and extra Companies/Mapped/WhatsApp/Attendance routes are retained. Employer fields are implemented, but this is not the PDF's exact employer-as-Client and ten-item sidebar. A deliberate migration/product decision is still needed for literal alignment.
- **Scale:** Data Bank, Inbox and order matching are paginated on the server; skill groups aggregate the current database pool. Global search and some record pickers still depend on bootstrap collections; reporting reads a bounded-field aggregate of the database into application memory. Large-volume acceptance and query plans remain outstanding.
- **History:** owner snapshots and assignment/escalation/missed-update events are reliable for newly recorded activity. Pre-migration history cannot be reconstructed exactly; reports disclose inferred legacy owner attribution and absent historical events.
- **Communication scope:** Zoho supports folder operations, synchronized read/star state, plain-text compose/reply/forward, attachments and durable drafts. SMTP acceptance is not final recipient delivery; unknown/partial sends require reconciliation. Attachment search is exact over stored CRM history, not the entire unopened remote mailbox. Historical import is bounded and explicit. Reviewed multi-person splitting and optional acknowledgements are implemented with durable recovery; production provider acceptance remains separate.
- **Time:** to-do reminders scan every 30 seconds plus bell polling; SLA/daily checks run every fifteen minutes. Presence expiry and browser event behavior need deployed elapsed-time acceptance. Attendance is intentional clocking; foreground presence is a separate approximate signal.
- **Live integrations:** no real Zoho authentication/mail send, WhatsApp delivery, paid Veriis extraction or S3 bucket acceptance is established by synthetic fixtures. Actual provider policy, credentials, callbacks, object retention/restore and deployment migration remain explicit acceptance steps.
